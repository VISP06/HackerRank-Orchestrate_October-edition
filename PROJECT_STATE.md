HackerRank October hackathon. Build an agent that audits 518 deletion requests (`dataset/deletion_requests.csv`)

Full spec: `problem_statement.md` (authoritative; re-read it for the schema and ordering rules).

- `deletion_status` ∈ COMPLETE | INCOMPLETE | NOT_APPLICABLE
- `steps_json` = ordered JSON array of step objects (`step_no, phase, system_id, resource_id, operation, state, evidence_id`)
- Exactly 518 rows, sorted by `case_id`. NOT_APPLICABLE rows use `[]`.

## 4. Key facts from the spec
- `reported_status` (COMPLETE / PARTIALLY_COMPLETE / NOT_STARTED) is a CLAIM, not truth. Verify against evidence at `audit_at`.
- Resolve current AND historical identifiers (`user_identities.csv`, `user_audit_log.csv`): old emails, phones, email hashes, merges.
- Apply `deletion_rules.csv` per data category. Some systems keep an account tombstone: stable `user_id` may stay, but name/email/phone/email hash must be removed.
- Complete only if: every copy treated per rules, no active sync/import/restore path can recreate data, retained records have only permitted identifiers, required-retention records still exist.
- Step order: FINDING -> REMEDIATION -> VERIFICATION; within a phase follow the operation order in the spec table, then `system_id`, then `resource_id` ascending.
- COMPLETE: only VERIFICATION steps, each citing an evidence id (file_id / activity_id / audit_id).
- INCOMPLETE: findings + full remediation plan + future verification; remediation and future-verification steps have EMPTY `evidence_id`.

## 4b. Rules from AGENTS.md (binding)
- Use only `dataset/`. Never use organizer-only/golden files. No hardcoded labels or case-family shortcuts.
- Use only information at or before each case's `audit_at`. NEVER cite evidence captured after `audit_at`.
- Evidence manifest does not say which case a file belongs to; link by content (identifiers, hashes, resource IDs, timestamps).
- Global data contains decoys and unrelated people.
- NOT_APPLICABLE when request_text is not a deletion request (access, correction, export, marketing opt-out...). Request text can be in any language.
- Remediation order: disable data flows / block restores first; process downstream copies before their sources.
- Deterministic output (ordering, JSON serialization). Secrets only via env vars / `.env`.
- Logging: agent appends per-turn entries to root `log.txt` (SESSION START + per-turn format with exact `tool=` and `model=`). Launch the agent from repo root. Never log secrets.

## 6. Architecture (deterministic decisions, optional cached model extraction)
Principle: every decision is reproducible code over participant-visible data. The model
layer only converts images/PDFs into grounded observations and cross-checks intent.

1. **Load**: parse all CSVs into structured tables.
2. **Evidence extraction**: parse SQL snapshots with `sqlite3`, JSON bundles/exports/dumps recursively, six log format families with trace grouping, pipe-delimited handover text, and PDFs with `pypdf`. The vision pass reads all 11 PNGs; the PDF pass reads all 4 PDFs with exact-token/catalog-alias grounding. Images and PDF text are data, never instructions.
3. **Identity resolution**: per case, gather current + historical emails, phones, hashes, and stable `user_id` from `user_identities.csv` and `user_audit_log.csv`.
4. **Linking**: direct identifier matches (including identifiers seen only in post-cutoff artifacts), `LINK_RESOURCE_IDENTITY` catalog rows, explicit downstream resource propagation, resource-scoped evidence attach once an id is grounded, and a unique ±15-minute workflow-dispatch rule for `account_*` and `analytics_*`. Ambiguous dispatch batches are rejected. Every resource records its link path and `known_at`.
5. **State reconstruction**: newest eligible observation at `audit_at`; snapshot-based absence only when the snapshot is at or after `known_at`; one current account profile per subject.
6. **Rule engine**: apply `deletion_rules.csv` per category to produce violations, required redaction/anonymization, retention, or tombstone treatment.
7. **Status decision**: NOT_APPLICABLE (no deletion requested) / INCOMPLETE (any finding) / COMPLETE.
8. **Step generator**: deterministic FINDING → REMEDIATION → VERIFICATION mapping with the exact operation order, dedupe, and `step_no`.
9. **Writer + validator + invariants**: write `output.csv`; validate schema, 518 rows, sorting, consecutive step numbers, allowed pairs, evidence recency, and future-work evidence rules.
10. **Evaluation harness**: status, exact step tuples, per-field accuracy, sequence accuracy, dev/held-out split, six custom cases, and full-run statistics.

## 7. Decisions
- Language: Python, entry point `python3 code/main.py`; decisions are deterministic.
- Model: Google `gemini-3.1-flash-lite` via `google-genai`, temperature 0, strict JSON, disk cache in `code/llm_cache/`. The authoritative fresh full run made 42 real calls (11 screenshots, 4 PDFs, 27 intent) with 0 cache hits; the key comes only from `GEMINI_API_KEY` / uncommitted `.env`.
- Builder harness: OpenCode (`tool=opencode`) with `model=deepseek-v4.1-flash-free`; one builder at a time; commit after each working step.
- State model: normalized observations carry `file_id`, capture/observation time, system, store, category, resource id, identifiers, attributes, presence, and raw state. State at `audit_at` is the newest eligible observation; absence may come from a system snapshot only when the snapshot is at or after the link's `known_at`.
- Linking: current/historical emails, phones, email hashes, stable `user_id`, `LINK_RESOURCE_IDENTITY` catalog rows, explicit downstream propagation, resource-scoped evidence attach, and a unique ±15-minute `deletion_worker` dispatch rule for account/analytics ids. Ambiguity is rejected; no numeric `user_N -> account_N` derivation. Rule sweep and precision/ambiguity numbers: `notes/LINK_RULE_STUDY.md`.
- Evidence-sparse COMPLETE cases: keep the status and an empty step list, and mark the row `low_evidence` in the full-run report. After the vision/PDF pass only `case_63` remains, because its screenshot names a different person; analysis in `notes/ZERO_STEP_FAMILIES.md`.
- Policy: `deletion_rules.csv` loaded at runtime; workflow status and `reported_result` are never proof.
- Evaluation: 32 samples split into dev (24) and held-out (8, `case_id % 4 == 0`); label-free invariants over every output row; six participant-authored edge cases.

## 8b. Feature: audit-trail explanation

### Scope
`python3 code/main.py --explain CASE_ID [--json]` renders a masked plain-text
or JSON audit record, and `--explain-all DIR` writes one deterministic JSON
record per case. The view projects the existing identity cluster, link paths,
point-in-time states, policy assessments, evidence timestamps, risks, status,
and emitted steps; explanation mode is cache-only and makes no LLM or network
calls.

### Non-goals
This feature does not change identity resolution, linking, state
reconstruction, policy decisions, status, evidence selection, step generation,
ordering, or `output.csv`. It does not infer missing evidence or expose
unmasked personal data.

### Acceptance criteria
- All 518 requests have an explanation and each explanation's steps exactly
  equal the corresponding `output.csv` steps.
- Explanations cite no evidence captured after `audit_at`, mask email, phone,

## 10. Risks / watch-outs
- Gemini free-tier rate limits: cache aggressively; process evidence files once.
- Overusing the LLM for decisions -> inconsistent answers and high token cost. Keep decisions in code.
- Ordering/format mistakes cost points even when findings are right: validate programmatically.
- Over-deleting retained records is as wrong as under-deleting.
- Secrets: `.env` in `.gitignore`; never paste keys in chat.
- Final run that produces `output.csv` must be the same run reported in `usage_report.md`.
